### PIT-028 — Backend failure must withdraw a prior fee vote

Status: confirmed implementation trap; runtime regression added. WAL-004 permits a guardian's optional fee vote to become absent and says an unavailable backend proposes absence. Skipping `fee_rate()` errors leaves that guardian's old present vote in replicated state indefinitely. Propose `FeeRate(None)` on backend failure through ordinary ordering; never directly edit the stored vote. A real single-guardian runtime regression exercises present → backend error → absence → restored estimate → present, then successful missing estimate → absence. Repeated absence still follows WAL-004's stored-vote duplicate rule.

### PIT-029 — Reachable backend without an estimate is a separate definition gate

Status: normative clarification outstanding; Q16. WAL-004 names backend availability, while Core can successfully answer `estimatesmartfee` without a `feerate`. Exact-baseline reference votes of `Some(1000)` were observed alongside such a Core response; that black-box observation alone does not establish the source/fallback algorithm. Keep `CoreRpc::fee_rate()` honest (`Ok(None)`); do not invent a fallback, rewrite returned data, or change received-vote admission to make monetary tests progress. Clarify the proposer mapping and the operator handoff's null-quote statement independently of PIT-028's error-withdrawal fix.

## PIT-030 — Operational DNS must not inherit a process-wide startup failure timer

Status: confirmed integration defect, corrected. Dynamic endpoint refresh initially reused a synchronous DNS helper guarded by the daemon-wide 15-second watchdog. A slow lookup for one signed operational destination could terminate the guardian rather than leave that peer parked. The process now runs DNS in an owned same-executable helper with bounded output, deadline/cancellation and kill-plus-reap cleanup. No resolver thread is detached and an unresolved peer does not cause fallback to its obsolete URL. Five resolver tests and actual daemon process/endpoint-refresh/restart tests pass. OS-level scheduling and uninterruptible I/O still bound any absolute wall-clock guarantee.

## PIT-031 — Written native JSON examples can disagree with the pinned executable

Status: confirmed spec/baseline conflict; user authorized the reference format on 2026-09-11 (Q17). Historical conflict observation: All four guardians discovered a real deposit, but the existing CLI could not read our WAL-016 object-form Bitcoin outpoint; both reference guardians returned a display `txid:vout` string instead. Preserve JSON, Bitcoin serialization and Fedimint output-location types as separate boundaries. Correcting a JSON response must not alter signed transaction bytes or persisted module state. Populated wallet-result outpoint formatting still requires its own observation. Public response fixtures are in `tests/fixtures/interop/wal016-outpoint-conflict`.

User decision on 2026-09-11: match reference Bitcoin outpoint strings and record WAL-016's object form as a spec bug. Discovery has a retained-reference regression; fresh all-four live captures now also confirm populated Wallet strings. Distinct Fedimint output-location requests remain objects.

## PIT-032 — Successful broadcast is not confirmation or an accounting transition

Status: documented trap, real Wallet process-crash regressions pass. WAL-008/009/015/017 distinguish accepted construction, threshold signing, broadcast and scanned confirmation. Keep signed-unconfirmed transactions retryable even after a successful backend acknowledgement; a process may die after delivery but before receiving that acknowledgement. Retry the committed signed bytes, without recreating the claim, issuing new shares, changing balances or deleting the job merely because the backend accepted it. `tests/mint_wallet_atomicity.rs` kills an owned process before broadcast and after controlled delivery before acknowledgement, reopens every namespace, and verifies identical retries after repeated reopen. This is process-crash evidence with a controlled backend; actual Core admission and host power-loss behavior remain separate requirements.

## PIT-033 — A persistence error does not promise that nothing committed

Status: documented durability trap; OS write-failure tests pass. NET-009 and CON-010 require acknowledged agreement data and accepted application effects to survive restart. After a persistence error, stop the affected execution path and recover authoritative stored state; do not infer rollback from the returned error or acknowledge success. `tests/storage_failure.rs` applies a file-size limit only to an owned process, requires a real write-failure signal and an API error, kills/reaps it, and checks that acknowledged data survives and attempted changes recover wholly before or after. The session-completion case also ties completed outcome/count, pending history and agreement cleanup together while preserving Wallet state. It exercises the shared completion transaction under n=1/q=1; four-engine shutdown/replay has separate tests. This does not establish every filesystem error mode or host power-loss behavior.

## PIT-034 — CLI receipt acknowledgement is not completed reissuance

Status: observed external-driver trap, not a newly established consensus-spec bug. The pinned CLI's Mint receive help promises reissuance and an amount, but the observed result was the string `"Success"` followed by an empty immediate note count. Do not conclude either final receipt or consensus rejection from that pair alone. Keep the same durable client running with the public `dev wait-complete` command, then verify its notes and accepted history. Never resubmit a token to recover an ambiguous receipt. The first driver attempt stopped too early; its reissuance remains unproven.

## PIT-035 — A reissuance can include notes already owned by the recipient

Status: confirmed test-driver matching error, not a consensus-spec defect. In the fourth monetary survivor case, the external client combined all six exported notes with eight notes already in its inventory. The accepted transaction in signed session 8 had fourteen Mint inputs and seven Mint outputs, certified by the three surviving guardians. Requiring its complete input set to equal the exported token rejected valid observed behavior. Correlate every exported note exactly once and require one unique target transaction, valid bounded Mint inputs/outputs and the required certificate signers; allow additional authorized Mint inputs. Do not infer client coin-selection policy from earlier simpler transactions. This finding does not establish the interrupted guardian's subsequent recovery.
