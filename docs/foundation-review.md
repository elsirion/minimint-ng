## API listener and handler integration checkpoint

Coordinator ran `cargo test --locked --test setup_api --test api_server --test websocket --test rpc --test json --test core_api --test module_api --test config_api --test backup_api --test announcements`: all 68 entries passed across these ten targets. This validates real loopback WebSockets and the independent handler/storage tests together, not a running federation executable.

The listener bounds connections and in-flight messages, keeps one reader processing controls, and serializes all response/control writes through one write state. Per-connection cancellation propagates to cooperative handlers and all workers are joined. Same-connection long poll/fast request/pong, late-success suppression, disconnect, saturation, response bounds and interrupted writers have regressions. Further review corrected mutex waits to use deadline-aware try_lock rather than checking a deadline only after a blocking lock; the extra writer-lock regression passes separately. A native engine or handler that ignores cancellation still requires the daemon's process-level watchdog; no forced thread termination or hard native join deadline is claimed.

Setup API passes three tests after review corrections: identical parameter/peer-code retries remain idempotent after the one-shot driver handoff, genuinely changing calls are frozen, and a disconnected driver channel is tested after all generation preconditions are satisfied. A successful start_dkg means only that the exact map/identity was queued. Running status is a daemon transition after persistence and service installation, not a DKG queue acknowledgment.

Core polling handlers expose CoreFailure::Fatal and ::Storage separately from ordinary RPC errors. Tests preserve that distinction for real Wallet unsupported fee arithmetic and corrupt persisted history while public errors remain sanitized. Submission enqueue is never returned as acceptance, full queues retry without requiring a state change, competing accepted spends cause revalidation, and session boundaries cause reproposal. The daemon must register its wake token before polling.

Configuration APIs preserve explicit caller-supplied capability summaries, complete dynamic module payloads and distinct commitments. Signed announcement/metadata tests verify exact domains and original metadata text, monotonic updates, future-time limits and durable reopen; typed signing helpers do not establish the missing admin JSON schemas. Backup review finds no material defect for normalized producer timestamps; Q15 retains the non-normalized interpretation as an evidence/definition gap.

These are component integration results, not a daemon executable or Bitcoin/upstream monetary run.

Independent service review corrected constructor cross-wiring: API state and configuration now derive from the actual runtime handle, including the configuration response and signing identity. Authentication precedes missing signing-schema errors. The runtime owner reports 11 controller tests plus session/core regressions passing; independent read-only review confirms engine-before-pump shutdown, joined worker guards, cancellation on worker failures, per-commit notifications outside the writer, and backup retention on failed shutdown. Directly forcing idle native-engine exit at the runtime layer remains a test gap; the health check is present by inspection.

Startup options share the runtime's canonical `fedimint://` authority contract. Private-file opening uses Linux x86_64 O_PATH/O_NOFOLLOW, validates the reference descriptor before any read-open, reopens its retained inode through procfs and verifies type/permissions/inode again. Bounded subprocess regression covers FIFO and other non-regular rejection. Constants were checked against the pinned environment's public C headers; no dependency or unsafe code was added. Linux x86_64/procfs is an explicit current deployment requirement, and ordinary filesystem latency is not claimed to have a deadline.
