# Daemon interfaces — implementation contract v1

Status: foundation contracts frozen on 2026-09-10. Later module/API contracts below define ownership and invariants; concrete downstream signatures are finalized at their dependency gate. Changes require coordinator review and dependent test updates. Source authority remains the pinned spec, not Fedimint code.

## Shared conventions

`src/protocol/mod.rs` owns `PeerId(pub u16)`, `ModuleId(pub u16)`, `Version { major: u32, minor: u32 }`, `OutPoint { txid: [u8;32], out_idx: u64 }`, and `DynamicValue { module_id: ModuleId, payload: Vec<u8> }`. These are wire identities/bytes, not a claim of authenticated or cryptographically validated objects. Derive equality/order/hash as appropriate. UTF-8 string ordering is Rust byte lexicographic order. Monetary values in core are u64 millisatoshis; Bitcoin amounts are explicitly named satoshis.

`ConsensusEncode::consensus_encode(&self) -> Vec<u8>` and `ConsensusDecode::consensus_decode(reader: &mut Reader<'_>) -> Result<Self, DecodeError>` are local wire contracts. `decode_whole<T>` calls the decoder then `finish()`. Existing `Reader` and `DecodeError` remain owned by codec lane; add variants for unsupported/malformed schema cases as required, without conflating unknown opaque values with execution permission. Streaming network limits belong outside the finite-buffer reader.

Protocol transaction decoding accepts raw framed module data for inspection. Execution decoding additionally takes the configured module registry and validates exact module payloads before acceptance. `Transaction` contains ordered dynamic inputs/outputs, nonce `[u8;8]`, and `TransactionSignatures` (tag-0 list of raw64 or unknown tag/body). `commitment_bytes()` excludes signatures; hashing is applied by the crypto/core caller so wire types do not depend on crypto. Unknown transaction signature scheme is retained and rejected during authorization.

## Crypto lane

`src/crypto/mod.rs` owns `CryptoError` and hash/random functions. `sha256(&[u8]) -> [u8;32]`; `hmac_sha512(key: &[u8], message: &[u8]) -> Result<[u8;64],CryptoError>`; `random_bytes<const N: usize>() -> Result<[u8;N],CryptoError>`. No mnemonic or client-root derivation module.

`src/crypto/secp.rs` provides a non-Debug, non-Copy `SecretKey` constructed from valid 32-byte big-endian input or OS randomness. It exposes compressed public key, exact-prehash BIP340 signing, low-S compact ECDSA signing, and additive secret tweak; byte export only for private durable configuration, never diagnostics. Public operations validate compressed keys, verify Schnorr/low-S ECDSA over exact 32-byte messages, and tweak public keys. Return `CryptoError` for invalid objects; error messages never contain private inputs. The lane reports exact finalized method signatures before consumers start.

`src/crypto/bls.rs` owns validated scalar/G1/G2 types. Canonical public parsing checks lengths, compression, coordinates, curve and subgroup, with spec-permitted zero/infinity. Support polynomial/share arithmetic, scalar/point multiplication, pairings, generator construction, and exact seeded G1 Mint mapping. `verify_share` and interpolation keep caller threshold/distinct-ID validation explicit. Secrets have no revealing Debug. Any raw native FFI is confined to `src/crypto/bls_ffi.rs` with explicit length/lifetime safety comments and local unsafe permission; package default remains deny.

## Storage lane

One cloneable `Store` handle owns a single database and serializes write transactions. `Store::open(path: impl AsRef<Path>) -> Result<Store,StoreError>`; `snapshot() -> Result<Snapshot,StoreError>`; `transaction() -> Result<WriteTransaction<'_>,StoreError>`. Snapshots expose owned/copy-out byte values with `get(namespace: Namespace, key: &[u8]) -> Result<Option<Vec<u8>>,StoreError>` and ordered `scan_prefix(...) -> Result<Vec<(Vec<u8>,Vec<u8>)>,StoreError>`. Writers support the same reads plus `put`, `delete`, and consuming `commit(self) -> Result<(),StoreError>`. Dropping a writer rolls back. The writer must see its own writes. Commit success means durable media sync, not merely OS buffer submission. API checks drop their transaction without commit.

`Namespace` is a closed enum: `Replicated`, `Local`, `Agreement`, `Outbox`, `ClientBackup`. Prefix namespace bytes internally; do not expose database encoding as consensus encoding. Ordered scans use lexicographic key bytes; schema owners must choose sortable index encodings deliberately. All namespaces participate in one atomic commit when needed. No nested writer transactions.

`append_agreement(session: u64, bytes: &[u8]) -> Result<(),StoreError>` durably appends exact supplied bytes before success. `read_agreement(session) -> Result<Vec<u8>,StoreError>` concatenates committed chunks, without interpreting them. `clear_agreement` is a method on the write transaction so session-completion storage and cleanup can commit atomically. No accepted-item reconstruction of these bytes. Multiple Store handles to one path must not permit independent unsynchronized writers; choose database locking accordingly.

Use a mature substantial storage library rather than implementing a new journal. The lane must propose a dependency and verify its public API durability/transaction capability before adding it through the coordinator. Process-crash tests are required. Persist private keys with restricted file/directory permissions as applicable; storage encryption is not claimed without an explicit design.

## Downstream gates

- `ValidatedConfig` is immutable, constructed only after key/peer/module/version validation; raw wire config is a distinct type. Private guardian shares and transport keys never enter public commitments.
- Module transitions use `&mut WriteTransaction`, configured instance ID, transaction outpoint and/or proposing `PeerId`. Inputs return amount/fee/authorization key; outputs return amount/fee; consensus items report acceptance or a typed rejection. Closed Mint/Wallet dispatch and exact error precedence are coordinator-owned.
- `FinalizedUnit` carries creator, round and optional data; every engine unit is delivered in order. Session owns accepted-item replay, header/signature phase and atomic completion. Engine stop is awaited before cleanup.
- Bitcoin RPC produces local observations for proposals and serves agreed scans; broadcasts consume persisted outbox work after commit. No RPC handler mutates replicated state outside ordered execution. The daemon selects exactly one adapter (`daemon::bitcoin::Backend`): loopback Core JSON-RPC (`CoreRpc`) or Esplora over HTTPS (`bitcoin::esplora::Esplora`, polled every 5 s instead of 1 s).
- Server APIs read committed snapshots and wait on accepted-state notifications. Full endpoint/capability inventory is a separate D0 artifact. Peer history RPC uses configured module decoders. No new wallet client is introduced.

## Accepted runtime configuration contract

`daemon::config::RuntimeConfig::from_persisted(setup::PersistedSetup)` consumes the stored public configuration and private keys and returns immutable startup objects or a sanitized `RuntimeConfigError`. It performs no DNS lookup or listener binding. It is the startup validation boundary; raw configuration decoding and `RawServerConfig::check_two_module_profile` do not substitute for it.

The implemented profile supports one guardian or 4–20 guardians. The upper bound belongs to Wallet's CHECKMULTISIG construction domain (WAL-012), not the generic peer-ID or Aleph domains. Core consensus is 2.1, both module consensus versions are 1.0, and the stored compatibility release is normalized `0.13.0`. The positive round count must satisfy the NET-009 `R + 1000` u16 bound. Setup records, TCP API endpoints, broadcast keys and TLS certificate maps must have identical contiguous peer IDs; local membership, public keys, local secret correspondence, retained endpoint/name/certificate bindings and module payloads are checked. Wallet's key map must match the guardian membership and its network must match setup. Modules are selected by kind, preserving distinct configured instance IDs. Mint validation retains MINT-012's required local-share checks without adding aggregate reconstruction or remote-share map equality predicates.

The object owns `Modules`, `TlsConfig`, the immutable `RawServerConfig`, remote TCP URLs and the private broadcast key. Share it through `Arc<RuntimeConfig>`. Public methods are `peer() -> PeerId`, `modules() -> &Modules`, `server_config() -> &RawServerConfig`, `tls_config() -> TlsConfig` and `remote_peer_urls() -> &BTreeMap<PeerId, CanonicalUrl>`. `session_config() -> Result<core::session::SessionConfig, RuntimeConfigError>` supplies the exact stored peer keys, version and rounds, cloning the broadcast scalar through a zeroized temporary. Neither runtime configuration nor its secret-bearing children have revealing diagnostics.

TLS construction checks canonical, distinct DER certificates and exact local identity correspondence and installs the existing configured trust policy. Authenticated handshakes remain the certificate-chain, server-name and validity-time verification boundary. Startup validation does not promise that every peer is reachable or that a later certificate validation will succeed.

`resolve_peer_addresses() -> Result<BTreeMap<PeerId, SocketAddr>, RuntimeConfigError>` is a separate local I/O operation over remote `fedimint://host:port/` URLs transported over TCP. The crate-visible `tcp_authority` helper validates this same scheme, explicit port and root path for CLI and runtime callers; it never rewrites committed URLs. Resolution excludes the local peer and selects one resolved address per peer, preferring IPv4 when both families are available. General URL normalization, IPv6 URL literals and live DNS address rotation are outside the current simple-URL profile. The process driver supplies its listener bind address independently of the local advertised URL. Local agreement delay and API capability advertisements also belong to the driver; successful configuration validation creates neither timing defaults nor an automatic version advertisement.

## Ownership

D6 execution operates inside the caller's tentative storage transaction. `apply_consensus(&mut WriteTransaction, &Transaction, &impl ModuleTransitions, Version)` returns the accepted ID and records output module IDs, but never commits. The session caller must add history and audit before commit and drop the entire writer on any error. `check_submission(&Store, ...)` checks an existing accepted ID before witness validation and otherwise always rolls back. Accepted-ID keys are private `core/accepted-tx/v1/` plus raw32 in Replicated; values encode ordered module IDs. This is not a database interoperability promise.

`ModuleTransitions` is an internal executor/testing interface; production registration remains a closed Mint/Wallet dispatch. Inputs report u64 millisatoshi amount/fee and a compressed authorization key, outputs amount/fee. Storage failures remain infrastructure errors; module errors retain their instance and exact payload. Stateless module rejection maps to InvalidWitnessLength. Audit uses checked signed64 addition over module contributions and treats overflow/negative totals as fatal invariants. Real cross-module rollback is covered by tests/modules.rs and tests/mint_wallet_atomicity.rs, including populated consolidation and late funding failure. Synthetic transitions alone would not establish that boundary.

Worker A owns codecs/protocol files and their tests. Worker B owns crypto files/tests. Worker C owns storage files/tests. Coordinator owns Cargo/lock/shell, src/lib.rs, module registration, interface changes, daemon/profile files and the shared evidence/risk logs. Workers report proposed dependencies before use and do not edit shared roots. Reviews may add only specifically assigned regression files or request fixes from the owner.

## Ordered controller and running API composition

`Runtime::start(Store, Arc<RuntimeConfig>, Arc<PeerNetwork>, Arc<B>, RuntimeOptions)` returns an owned controller and cloneable `RuntimeHandle`. `B: RuntimeBackend` extends the Bitcoin backend with idempotent, nonpanicking cancellation and finite call cancellation/deadlines. Ordinary options use 50 ms round delay; tick, queue capacity and wallet polling are local scheduling policies. The controller owns session execution, wallet proposals/outbox polling and an independent network pump. All workers are joined; the pump remains alive until native agreement shutdown completes. `Session::abort` propagates shutdown failure and preserves recovery records. No hard native shutdown deadline is promised.

The handle exposes proposal submission, current session, bounded typed history submission, revision/wait notifications and stop state. Queueing is not acceptance/adoption. A per-commit notifier runs outside the database writer so blocked subsequent scans cannot hide earlier durable progress. Internal handles carry the exact store and immutable configuration used by the ordered worker; crate-private accessors supply API construction.

`RunningApi::new(RuntimeHandle, RunningApiOptions)` builds configuration responses and signed-update identity from that same runtime. Options supply software identity, explicit supported-version summary and protected access/admin secrets; no independently constructed database or public configuration can be substituted. `Service` atomically switches from setup to an installed `Arc<RunningApi>` after the lifecycle driver finishes persistence and starts the runtime. It releases its switch lock before handling requests or waiting. Long polls capture the runtime revision before checking a snapshot and observe connection cancellation at bounded intervals. Fatal persisted-state errors request runtime shutdown; the outer lifecycle must observe that stop, close the server and join all owners.

The one real-socket daemon API integration test covers single-guardian durable acceptance, altered-witness accepted duplicates, module dispatch, administrator/access separation, opaque backup roundtrip and cancellation. Subsequent daemon_process, daemon_shutdown, four_daemon_process and mixed_daemon_process evidence covers setup-to-running publication, bounded process cleanup and four-guardian APIs at the recorded scope; see the conformance/results ledgers. Full monetary and undefined operational schemas remain separate gates. Undefined diagnostic/signing schemas return explicit errors and cannot justify advertising the target API version.

## Live catch-up endpoint selection

`CatchupEndpoint::pending_announcement(peer, signed)` represents a stored signed override awaiting resolution; startup authenticates its configured peer signature and does not dial a fallback URL. `Catchup::select_announcement(peer, signed)` verifies signature and monotonic nonce, parks the selected peer and cancels its obsolete request. Identical signed fields are idempotent. `install_resolved(peer, &signed, addresses)` enforces the supported WS transport, matching ports and current selected fields before making a destination usable. Routing revisions prevent an in-flight stale selection from installing a socket. Other peers remain usable while one selection is unresolved.

The process owns announcement-store polling at a one-second interval. DNS runs in an owned helper process with a 15-second deadline; timeout or cancellation kills and reaps that helper without terminating the guardian. It parks before resolving, rereads durable announcements before installation, caches only successfully resolved selections, and retries failed resolutions. Reads use short snapshots outside request waits. No resolver thread is detached. The same executable provides an exact internal resolver mode before loading options, secrets or guardian workers; its parent drains a bounded nonblocking socket response and validates every returned address. Requested shutdown cancellation is normalized; unexpected runtime failure remains fatal. Catch-up tests cover authenticated history adoption, request deadlines, dynamic selection, stale/equivocal/forged updates, parked startup and joined cancellation. Actual-process RPC-to-refresh verification is tracked separately in the conformance ledger.

## Transport selection and Iroh profile

`--transport tcp|iroh` (default `tcp`) selects the setup-code endpoint variant of a fresh federation and must repeat the stored transport on restart (`lifecycle::ExpectedTransport`; a mismatch fails before networking starts). TCP keeps the mutual-TLS P2P and WebSocket API contract above. Iroh (SET-002 endpoint variant 1) stores two independent random Ed25519 endpoint secrets, never derived from consensus, Wallet or TLS keys: the API key serves API-002 over Iroh 0.35.0 (ALPN `FEDIMINT_API_ALPN`) and the P2P key carries NET-002 over Iroh 1.0.3 (ALPN `FEDIMINT_P2P_ALPN`). `net::TransportIdentity` holds either identity; setup record version 2 persists the Iroh secrets. SET-006: an Iroh setup commits the `(name, API key, P2P key)` map and leaves the TCP API and certificate maps empty. `RawServerConfig::client_api_endpoints()` derives the client endpoint map as `iroh://<64 lowercase hex API key>` with the guardian name; the federation ID, `client_config` and invite codes use that map, which matches the pinned reference byte for byte.

`PeerNetwork::start_iroh` reuses the TLS network's per-peer queues and semantics: NET-004 lower-identifier dialing, accepted replacement, disconnect on decode/send failure and no replay. Each envelope body is one finished unidirectional stream (limit 10,000,000 bytes, no inner length). Setup/DKG and agreement consume the same queues. `api::iroh::IrohApiServer` serves the installed `Service` handler: one bidirectional stream per request, `{"method":{"Core":name}|{"Module":[id,name]},"request":{"auth","params"}}` in, `{"Ok":value}` or `{"Err":{"code","message"}}` out; module methods map to the internal `module_<id>_<name>` naming. `IrohApiClient` is a dial-only Iroh 0.35 client for history catch-up; signed WebSocket announcements are not applied to Iroh catch-up endpoints.

Iroh components own small Tokio runtimes (two workers each) on threads joined by their owners; handlers remain blocking code and observe cancellation through `CallContext`. Local policies: 10s dial/handshake/read deadlines, 500ms redial, 128 API connections, 32 streams per connection, 60s operation deadline and 16 MiB API responses. The UDP endpoints bind the same `--api-bind`/`--p2p-bind` addresses; the TCP WebSocket listener on `--api-bind` remains for setup and administration. `--iroh-discovery` (default true) enables n0 DNS/pkarr discovery and default relays; `--iroh-address-file` supplies direct-address overrides; `--iroh-secret-file` imports the two secrets for a fresh setup only (a stored identity must match it). The WebSocket access secret is rejected with Iroh.
