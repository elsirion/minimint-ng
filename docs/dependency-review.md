# Dependency review

Reviewed 2026-09-10. This is a selection record, not a claim that the proposed guardian is implemented or interoperable. Only specification prose, the allowed baseline lockfile, and public library documentation/release metadata were consulted. No Fedimint implementation source or Aleph implementation internals were read.

## Initial decision

Start with one direct production dependency: `fedimint-aleph-bft = { version = "=0.36.0", default-features = false }`. Preserve its baseline transitive resolution and checksums, including both Aleph types versions, as required by [NET-014](../spec/06-guardian-network.md). An exact direct version alone does not preserve that graph. Keep the generated lockfile and verify the reachable package/version/source/checksum tuples against the baseline. Do not upgrade a shared transitive package to accommodate an unrelated new library; permit a separate version where Cargo allows it, otherwise defer that library or resolve the protocol constraint explicitly.

Implement small bounded utilities locally: checked integer conversions, fixed-width and common wire encodings, hex conversion, length limits, typed errors, and the narrow CLI. Protocol state machines and adapters remain local. Cryptographic arithmetic, TLS, durable storage, general JSON parsing, and an async executor are not small utilities. Avoiding a crate does not establish correctness of a replacement.

Raw BLS FFI is confined to `src/crypto/bls_ffi.rs`; the package lint is deny with that explicit local exception. OpenSSL is supplied by the pinned Nix environment; provider/RNG/hash concentration and native build execution remain shared risks.

The all-target inventory records features and build scripts; it does not imply every target's script executed.

Parallel versions retain shared lineage and maintenance channels. The [cryptography specification](../spec/02-cryptography.md) requires seeded pseudorandom point sampling. A library's standard BLS signing/hash-to-curve convenience API is not a substitute. For BTC-only mintv2, prove the required G1 mapping first; do not expand scope into deferred Lightning TPE solely to exercise a library.

The TLS specification allows a common TLS 1.3 suite and key-exchange group; an alternative need not reproduce every optional baseline group. Different validation defaults, including handling directly trusted self-signed leaf certificates, remain interoperability gates. An OpenSSL-backed wrapper and another OpenSSL-backed wrapper are one engine. OpenSSL and AWS-LC are different current projects, but related historical crypto lineage means complete independence must not be claimed.

## Shared failure points and conditional assessment

The table evaluates **what follows if a relevant bug exists and is triggered**. It assigns no probability that a component contains a bug. Trigger likelihood depends on the bug's input preconditions, enabled features, deployment and adversary access; none is known well enough here for numeric estimates. Shared dependencies are potential correlated failure points, not proof that every fault defeats the federation.

### Process signal boundary selection

Added exact `signal-hook 0.4.4` with default features disabled; the lock resolves `signal-hook-registry 1.4.8` and retains existing `libc 0.2.185` / `errno 0.3.14`. The resolver added exactly those two signal packages. Full metadata policy passes with no errors and the mandatory Aleph closure unchanged; exact checksums/features/build-script markers are in the inventory. No application unsafe signal code, iterator/channel features or custom signal callbacks are introduced. Only the safe atomic-flag registration and immediate process-exit APIs are used.

Primary release metadata records non-yanked releases on 2026-04-04 for [signal-hook 0.4.4](https://crates.io/api/v1/crates/signal-hook/0.4.4) and 2025-12-25 for [registry 1.4.8](https://crates.io/api/v1/crates/signal-hook-registry/1.4.8). The [flag API](https://docs.rs/signal-hook/0.4.4/signal_hook/flag/fn.register.html) avoids handwritten signal ABI and async-signal-safety mistakes; [immediate exit](https://docs.rs/signal-hook/0.4.4/signal_hook/low_level/fn.exit.html) supplies the watchdog fallback without cleanup or a core dump. These release dates establish recent activity, not absence of vulnerabilities.

The baseline lock already contains `signal-hook-registry 1.4.5`; the wrapper's absent package name and newer registry version do not establish implementation independence. `libc`, platform signals, the registry lineage and our watchdog are common failure points. A triggered failure normally threatens graceful shutdown or availability, and both new guardians failing together can exceed f=1. Memory corruption, unsafe library bugs or substituted build inputs can have critical consequences, including guardian-key compromise. Signal handling does not authorize transactions or change consensus; such critical effects require an additional compromised memory/build boundary. No numerical defect probability is asserted.

Alternatives reviewed were `ctrlc` (dedicated handler thread plus nix), a broader nix/signalfd integration, and rustix or handwritten ABI handling requiring new application unsafe code. The narrow safe flag wrapper was selected to reduce lifecycle and signal-safety mistakes despite shared registry lineage. The watchdog is ordinary application code, never a signal handler; it observes termination independently of blocking I/O and forces exit only on explicit startup/shutdown deadlines, never on missing quorum.

## Implemented dependency gate and residual concentration

The initial `Cargo.lock` resolves **79 non-root packages**, all reachable through the approved agreement dependency and all matching baseline name/version/source/checksum identities. This is the resolved **all-target** closure after unused feature dependencies are pruned, not a claim that 79 packages execute on the Linux host. The [inventory](dependency-inventory.json) records resolved features, build-script and procedural-macro target declarations from Cargo metadata; no package implementation was read to obtain them. It currently lists 18 packages declaring build scripts and 10 declaring procedural macros, including target-specific entries that are not necessarily compiled here.

`tools/dependencies.py check` verifies the recorded baseline digest, direct exact pin/default-feature policy, forbidden feature forwarding and alternate dependency aliases/locations, root lock reachability, and all resolved agreement identities/checksums. Ten regression tests exercise valid resolution, tampered checksums/versions/baseline metadata, stale root entries, feature forwarding, target/build aliases and overwrite prevention. Run it with `cargo test --locked`: the metadata gate is not a replacement Cargo resolver and does not prove a binary is reproducible or safe. Committing lock and provenance changes still requires review; an attacker able to replace both files defeats a local digest comparison.

A compromised build script or procedural macro can modify produced code or access build-environment secrets. That is a **potentially critical build compromise**, even if the package's legitimate runtime purpose is only formatting or logging. Lock checks prevent unnoticed resolution drift, not compromise already present in an approved archive. No complete advisory scan or source audit is claimed by this milestone. Avoid putting guardian keys in the build environment, retain toolchain/native provenance, and separate building from runtime key generation.

The Nix development shell pins both a nixpkgs revision and its content hash. Nix tooling, binary substitutes, rustc, LLVM, linker, standard library and the operating system remain build/runtime trust dependencies outside Cargo.lock. This initial shell is reproducible in inputs, not a completed bit-for-bit binary reproduction exercise.

Two minimint-ng guardians run the same code. A bug in our local codec, future crypto adapter, state machine or storage integration can affect **two of four** guardians and exceed the intended f=1 fault budget even when fedimintd uses different libraries. A full-agreement shared bug may affect all four. Diversity changes common failure exposure; it does not increase the protocol threshold or excuse independent tests. Local reimplementation reduces imported code for small utilities but adds our own correlated correctness risk.

### JSON selection and resolved graph (2026-09-10)

General JSON parsing is substantial functionality used by both server APIs and Bitcoin RPC. The alternative [simd-json 0.18.1](https://docs.rs/crate/simd-json/0.18.1) also provides a substantial parser with Serde integration. Sonic was selected for its checked owned-value interface and public raw-number mode, which permits exact decimal Bitcoin fee conversion without floating point. No parser is added merely to replace a small utility. This is a reviewed tradeoff, not a claim that Sonic is safer or completely independent.

Host `cargo tree -p sonic-rs --edges normal,build` includes arena allocation (`bumpalo`), byte/string containers (`bytes`, `faststr`), UTF-8/SIMD/number support, randomized hashing, Serde, error macros and number formatting. Sonic and several of these packages are shared across both new guardians; Serde and other package/native/compiler lineage overlaps upstream. A remotely triggered memory-safety or request-confusion defect may have high/critical impact, especially if it compromises authorization or guardian secrets. Allocation/parser failures can disable both new guardians and exceed f=1. Code-generation and build-script compromise may be critical regardless of runtime reachability. Maintenance cadence is evidence of activity, not an advisory-free guarantee.

The 36 newly resolved lock entries include optional archival/WASM packages absent from the enabled dependency tree even with `--target all`. They are retained in the inventory, not counted as active Linux guardian runtime code. Exact extra versions of `bumpalo`, `getrandom`, `thiserror` and its macro were reviewed outside the mandatory Aleph closure; optional hashbrown/WASM identities are separately recorded as inactive. Enabling those features requires renewed review. All active Aleph identities remain baseline-pinned; the dependency gate and its 13 policy tests pass with this graph. The executable inventory contains package checksums, features, procedural macros and build-script markers; these markers do not alone prove a package is compiled on the deployment target.

Checked parsing is wrapped in `src/json.rs`. Callers must supply finite body and nesting caps and validate endpoint schemas before transitions. Duplicate decoded field names are rejected. Raw-number mode and exact scaled-integer conversion are required for Bitcoin RPC monetary decimals; no `f64` conversion is allowed for those amounts. Numeric and parser boundary tests are distinct from endpoint conformance and live Bitcoin evidence, which remain integration work.

Bitcoin RPC uses no additional HTTP, URL or Bitcoin RPC client crate: the required loopback Core interaction is a bounded Content-Length HTTP exchange, typed hashes/blocks and six narrow backend operations. This local framing code is another shared failure point for both new guardians and must not be treated as supply-chain diversity without application review. The larger general JSON parser remains a reviewed dependency. Credentials and encoded header buffers receive best-effort erasure; parser/native/runtime copies are not guaranteed erased.

### Esplora HTTPS backend and signet profile (2026-09-30)

The signet deployment profile needs a remote Bitcoin data source (`--esplora-url`, e.g. Mutinynet's `https://mutinynet.com/api`) instead of a loopback Core node. **No package was added and `Cargo.lock` is unchanged**; the dependency gate and inventory are unaffected. Candidate HTTP/TLS clients (`ureq`, `reqwest`/`hyper` with rustls or native-tls, `minreq`) were rejected: each adds a substantial new graph (and `reqwest`/`hyper` would pull an async runtime this daemon deliberately avoids), and `rustls` would share the baseline's TLS engine. Instead the adapter reuses two already reviewed boundaries:

- **TLS:** the selected `openssl 0.10.81` binding (`SslConnector`, TLS ≥ 1.2, SNI, peer verification and hostname/IP verification through the public API). Trust anchors come from the native OpenSSL default store (the pinned Nix OpenSSL reads `/etc/ssl/certs/ca-certificates.crt`; `SSL_CERT_FILE` overrides it). This widens OpenSSL's exposure from authenticated guardian mTLS to parsing a public web server's handshake and certificate chain; the same provider-concentration notes above apply. A TLS or CA compromise lets an attacker feed chain data, see below.
- **HTTP/1.1 framing:** local bounded code in `src/bitcoin/http.rs` (one request per connection, `Connection: close`, 16 KiB head, Content-Length, plain `chunked` or close-delimited bodies, 64 KiB/8 MiB body caps, one deadline per request, cancellation before every blocking step; both Content-Length and chunked, or any other transfer coding, are rejected). JSON parsing uses the reviewed Sonic wrapper. DNS runs in the existing killable resolver helper (PIT-030), cached for five minutes and dropped after a failed connect.

Conditional impact: the Esplora service (and its CDN) is a trusted chain oracle for this guardian, exactly as a local node is. It can withhold data (stalling this guardian's block/fee votes and scans), report a wrong tip or fee estimate (bounded by the threshold order statistic across guardians), or serve blocks for a different chain. Returned blocks are decoded locally and must hash to the hash obtained for that height, which prevents substitution under a known hash but not a wrong height-to-hash mapping. Guardians sharing one public service share this failure point, including the other implementations if configured with the same URL; this is an operational concentration, not implementation diversity. Local HTTP framing code is common to every minimint-ng guardian.

### Iroh transport selection (2026-09-30)

**User authorization:** on 2026-09-30 the user explicitly requested Iroh networking for guardian P2P and the client API and authorized adding the `iroh` dependency. This section records that selection; it does not claim the Iroh stack is independent of the reference, audited, or free of vulnerabilities.

**Direct additions,** all exact baseline versions: `iroh =1.0.3` (renamed `iroh-next`, default features off, `tls-ring`) for guardian P2P, `iroh =0.35.0` (default features off) for the client-facing API, and `tokio =1.50.0` (default features off; `rt-multi-thread`, `time`, `sync`, `macros`) to own their runtimes. Both Iroh versions are needed: the pinned reference guardian speaks NET-002 P2P over Iroh 1.0.3 (its `--iroh-p2p-relays` option names "Iroh 1.0 relay URLs … for guardian P2P") and serves API-002 wallets over Iroh 0.35.0, with an optional transitional Iroh 1.0 API that is off by default here and not advertised. The two stacks do not interoperate with each other (different QUIC implementations `noq` versus `iroh-quinn`, and relay protocols), and the pinned `fedimint-cli` bootstraps through 0.35. Spec NET-002/API-002 name the same versions; aontas independently depends on both.

**Resolution:** the lock was seeded from the baseline lock's own identities so that Cargo reused the reference resolution. All 436 newly resolved lock identities are exact baseline-lock identities (name, version, source, checksum); nothing outside the baseline lock was introduced. Nine of them replace previously reviewed extra versions that the widened engine closure now reaches, which moved back to their baseline versions (`serde`/`serde_core`/`serde_derive` 1.0.228, `once_cell` 1.21.3, `js-sys` 0.3.83, `wasm-bindgen` family 0.2.106); their stale review records were removed. The inventory now lists 629 all-target packages: 92 engine-closure identities (see below), 500 other baseline-name packages and the 37 pre-existing distinct names; 107 declare build scripts and 56 are procedural macros. Rustls 0.23.38 resolves with the `ring` provider (the reference ordinary server build uses AWS-LC for its TCP TLS); Tokio's feature set is widened by Iroh's own dependencies (including `net`, `process`, `signal`, `test-util`).

**Engine-closure exception (target-gated):** Iroh 0.35 (`iroh-quinn-proto`, `pkarr`) enables `getrandom 0.2`'s `js` feature. The all-target lock therefore connects the engine's `rand_core 0.6.4 → getrandom 0.2.16` to `wasm-bindgen` and `js-sys`, and through `wasm-bindgen-macro-support` to `bumpalo`. Those two `getrandom` edges are declared under `cfg(all(any(target_arch = "wasm32", target_arch = "wasm64"), target_os = "unknown"))` in getrandom's published manifest and are never compiled for the Linux guardian. Every package on that path matches the baseline except `bumpalo`: the already selected `sonic-rs 0.5.8` requires `^3.19`, while the baseline pins 3.18.1, and one lock cannot hold both. `tools/dependencies.py` now accepts an engine-reachable non-baseline identity only when its own exact review lists the gating edges (`target_gated_edges`), each edge exists in the baseline resolution itself, and the identity is unreachable once those edges are set aside. The remaining 81 engine-reachable identities still match the baseline with checksums. Three new policy regressions cover a missing edge record, an edge absent from the baseline, and an attempt to exempt a host-reachable upgrade. This is a narrowing of the earlier "never exempt an agreement-reachable identity" rule for wasm-only paths and should be re-reviewed if the guardian ever targets `wasm32-unknown-unknown`.

**Other reviewed extra versions:** 36 new records approve baseline identities that share a name with an engine-closure package but are resolved only for Iroh (`bitflags` 1.3.2, `convert_case` 0.10.0, `derive_more`/`-impl` 2.1.1, `foldhash` 0.2.0, `gloo-timers` 0.3.0, `rand` 0.9.4/0.10.1, `rand_chacha` 0.9.0, `rand_core` 0.9.3, `send_wrapper` 0.6.0) or only for Windows targets (`windows-targets` 0.42/0.48/0.53 and their per-target crates).

**Alternatives:** an independent QUIC/Iroh implementation would have to reproduce Iroh's raw-public-key TLS handshake, relay and discovery protocols for two versions (NET-G3 records them as unspecified); that is not a small utility. aontas made the same selection. Using only Iroh 1.0 would break the pinned client's API bootstrap.
